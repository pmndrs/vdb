| thin bunny | **+194.3 % / 197.1 %** | +9.1 % / 10.9 % | **+122.8 % / 107.7 %** | −17.8 % / 17.0 % | 33.5 dB, +22.4 % | 25.3 dB, +68.8 % |

| worst \|bias\| | 194 % | 32 % | 123 % | 71 % | | |

- The phase moves the **truth** far more than our frames: the references differ by 24–41 dB and up to +91 % luminance
  (the report camera sits on the sun's side, so HG g 0.8 has almost no back-scattered light and dual-lobe's back lobe
  shows); our frames move by 33–57 dB, +2 to +27 %. So the default phase is first a look choice: dual-lobe is what his
  demos, our harnesses (k3-frame, k6-scenes) and the K6.R reference set have rendered all along.
- Accuracy: with HG our renderer fails badly where single scattering matters and the view looks into the back lobe
  (thin and absorbing bunny: +168 % and +194 % with 'neural', +123 % 'volume' diffusion; smoke +36 %). Every multiple
  scattering term we have exits isotropically (diffusion, two-sided, octaves) or is a fluence (the K6.N network, trained
  for HG g 0.8 but predicting isotropic fluence), so the forward-peaked HG lobe's missing back-scatter is not seen by it.
  Dual-lobe's back lobe makes the exit closer to isotropic. HG is better on the thick WDAS cloud ('frame' neural −3 % /
  −2 % vs −32 % / −26 %), where deep multiple scattering dominates.
- Net: dual-lobe is the more robust default for our renderer (median error 19.9 % vs 37.3 %, worst 32 % vs 194 % with the
  default 'frame' neural), and it matches his current default and his demos. The cost is WDAS's bias with 'neural'
  (−3 % → −32 %), and every default-phase image moves (luminance +2 to +27 % on these scenes).

**Owner question (K7.4).** Suggestion: make `'dual-lobe'` 0.8 / −0.3 / 0.2 the renderer's default phase. Pros: worst-case
bias at defaults 194 % → 32 % on the report scenes; his v0.30 default and his demos' phase (our parity harnesses already set
it, so his captures and the reference set do not move); closer to a cloud's Mie phase than one forward lobe (back-scatter,
the "silver lining" he names). Cons: WDAS 'frame' neural −3 % → −32 %; every image drawn with the default phase changes
(0.x: a CHANGELOG "Changed" line, docs, `k6-frames` frames that use the default; most harness frames set the phase and do
not move); HG stays the better choice for thick cumulus with 'neural'. Settling test: these groups
(`node scripts/k6/reference-report.mjs --groups=k74-wdas,k74-wdas-hg,… --reuse`) on the held-out K6.N media, plus
`e2e/k6-frames.spec.ts` before / after to list the frames that move. A longer-term fix for either phase is an
anisotropy-aware exit of the multiple-scattering term (the V128 / K6.Q1c dipole idea applied to the MS totals, or a g input
to the network, K6.N open question), follow-up K7.4c.

it is needed. Follow-up K7.4a: run 'neural' per channel in spectral mode (the network's inputs per channel: optical depths and
albedo), so turning spectral on stops costing the network; revisit the default after it.

## 4. K7.8: his PR #112 ("[Experimental] Points as Foam / Points as Liquid")

OPEN, not a draft, from his branch `jan/vdb-190-liquid-rendering-for-point-grids-screen-space`; one commit "Stash"
(`be6a1bf`) created 2026-11-15 and untouched since, branched before v0.24 (parent `0462e88`, PR #111); no body, no comments,
+2041 / −29. It is far behind his main and would conflict with v0.30's points defaults. Despite the title there is no foam
code.

What it does: `VDBLiquid` (both his backends), screen-space fluid rendering after Green (GDC 2010): points drawn as spheres
into a depth target and a half-resolution thickness target; a 2-iteration bilateral depth filter in world units (σ 0.7 r;
depth steps above 10 r stay separate surfaces); Gaussian-blurred thickness (2 r); normals from the smoothed depth; shading
with Fresnel reflection of the environment, the specular of up to 8 lights, refraction of the frame drawn before, Beer-Lambert
water absorption (IOR 1.333, Pope & Fry 1997) and soft edges where thinner than a point; it writes depth. Options
`radiusScale`, `blend`, opt-in `lod` (thinning where the point spacing is under 3 px), `maxPoints` 1e6. API: `FrameVolume`
`points: 'liquid'`; `createPointData()` gains `radii` from the `pscale` float attribute.

For us: no format work (we already read `pscale`: `vdbPointRenderData(…, { attributes: ['pscale'] })`). A liquid mode would
be a new host-seam renderer beside K6.6's point pass: the splat and the filter as core kernels with CPU twins, the composite
as a host function (as `vdbFrameIntegrate`). Not worth porting before he merges it; it then shows in the upstream watch as a
release. K7.8 is closed as research; no follow-up row.
