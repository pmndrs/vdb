## 1. Sources

**What the frame renderer reads.** `VDBFrameRenderer` reads only the handle: a dense source's `volume` (into the core's
`vdbDenseSource`), a sparse source's pool, ids, `lod` / `normalize` / `followImage` / `fastTrilinear` /
`cacheAccessor` / `pyramidMax`, boxes and stats (into a `vdbSparseSourceGpu` slot). It never sampled the three-side
textures or pyramid, but before K6.8a they were made anyway:

- `vdbDenseTextures(volume)` uploaded every channel as three `Data3DTexture`s at creation, and the core uploaded the
  same texels again: a frame-only dense source held them twice.
- `vdbSparseSource(…)` built its own coarse pyramid at creation (r16f textures, the `vdbCreateBoxPyramid` scratch
  buffers and a GPU build), and rebuilt it on every `followImage` relayout; the core built its own beside it.

**Now.** Both are handles; the three-side GPU resources are made on first use by a custom TSL material:

- Dense: `textures` is a getter that uploads on first access (`vdbVolumeUniforms` or user code). `replace()` before
  that only swaps the volume, stats, `version` (resize / new box) and keeps the channel shape (missing channels become
  their absent value, as before). `VDBFrameVolume` checks `source.volume`, not `source.textures`.
- Sparse: `sparse-source.ts` keeps the handle (validation, boxes, stats, `refreshStats`, the `followImage` layout,
  `version`); the TSL half moves to `sparse-nodes.ts` (`VDBSparseNodes`: the pyramid, `createUniforms`, `createNodes`,
  the probe `wgslFn`s). It is made by `source.pyramid`, `vdbVolumeUniforms`, `vdbVolumeNodes`, `nodeAverageFn()`,
  `skipEmptyFn()`. `lodLevels` comes from `vdbBoxPyramidLayout` (the same numbers the pyramid had). `gpuBytes.pyramid`,
  `pyramidScratch` and `pyramidBuilds` are 0 until then. The GPU-pyramid prerequisites (an initialized renderer,
  `initTexture`, `images.density` for `'cpu'`) are still checked at creation.
- `VDBFrameRenderer.coreVolumeOf(volume)` (`@internal`): the core volume behind a frame volume. Demo 15 reads its LOD
  bytes from the core source (`slot.source.gpuBytes.atlas` / `pyramidScratch`); it showed the unused three-side
  duplicate before.

**What stayed TSL, and why.** `VDBVolumeMaterial` does not use `vdbVolumeNodes` / `vdbVolumeUniforms` or any source
pyramid: it marches the pool through `VDBGridNode` directly (the brief's premise that it needs them is wrong). The TSL
half serves only custom TSL materials (his `createVolumeNodes` shape, public since 0.1) and the K3 harnesses
(`k3-dense`, `k3-pyramid ?three=1`, `k3-sparse`'s probes, `wvdb-sampling`). It stays because it is public API.

**Lines** (`packages/vdb/src/three`, `wc -l`): 6,485 → 6,747. `sparse-source.ts` 1,074 → 670 plus `sparse-nodes.ts` 565;
`volume-source.ts` 603 → 632; `volume-shadows.ts` 462 → 499; `renderer.ts` 513 → 523; `grid-node.ts` 639 → 659. The
gain is behavioural (no duplicate GPU work or memory; one receiver implementation), not a line count: the TSL ports
removed from `volume-shadows.ts` (~130 lines) were replaced by the stand-in, placeholder and view-loader code and its
docs. The K6.8 estimate of "~1,000 lines" assumed deleting the TSL half, which needs the owner (below).

**Owner question: delete `vdbVolumeNodes` / `vdbVolumeUniforms` (and with them the sources' TSL half)?**
- Suggestion: deprecate in 0.2.0, delete in 0.3.0; the core's `vdbSparseSourceGpu` / `vdbDenseSource` `wgsl()` are the
  supported way to sample a source in a custom shader.
- Pros: about 1,100 lines go (`sparse-nodes.ts`, the TSL parts of `volume-source.ts`, the `pyramidBuild: 'cpu'` path);
  one pyramid implementation; no lazily-made GPU state on the handles.
- Cons: a public 0.1 API used by anyone who ported his materials to TSL; the K3.2 harnesses that check the TSL path
  (`k3-pyramid ?three=1`, `k3-sparse` probes, `k3-dense`, `wvdb-sampling`) move to the core probes (`k6-sparse` covers
  the core's sparse WGSL).
- Settles it: a `grep` of the consumer repos (read-only) for `vdbVolumeNodes` / `vdbVolumeUniforms`; if none, delete.

## 2. Receivers through the core WGSL

`three/frame/volume-shadows.ts`: each shadow light's receiver is a `wgslFn` wrapper around the core's own
`vdbVolumeShadow` / `vdbVolumeShadowRgb` / `vdbVolumeShadowCube` / `vdbVolumeShadowCubeRgb` (`vdbVolumeShadowWgsl()`,
one code node per shader; nothing under `core/frame/wgsl` changed). Inputs:

- the map: `texture(standIn)` (2d-array) or `cubeTexture(standIn)` passed by reference, `sampler(node)` its sampler;
  the rgb twin likewise (spectral maps);
- the map's `view` buffer (`VdbVolumeShadowView`, rewritten by the core each update) bound through a **storage
  stand-in**: `vdbThreeStorageStandIn` (`grid-node.ts`, the `VDBGridNode` pool-buffer pattern and its self-test) and
  `storage(attr, 'uvec4', 24).toReadOnly()`; a per-light code node (`VDBFrameShadowViewNode`) generates
  `vdbFrameShadowView<k>()`, which unpacks the struct from its 24 `vec4u` words (`vdbFrameShadowViewLoaderWgsl`,
  generated from `VDB_VOLUME_SHADOW_VIEW`'s layout; a unit test pins the words). three binds foreign buffers only as
  storage (a uniform `BufferNode` uploads its own array), so the core's view buffer gains `STORAGE` usage
  (`core/frame/shadows.ts`, one line; the only core change).
- `viewDepth` = `-positionView.z`, `world` = `positionWorld`; a ShadowMaterial over a spectral map takes the rgb mean.

Gone: the TSL ports of the lookup (cascade pick, spot projection, cube lookup, Beer depth), the per-light uniforms
copied from `drawn` each update, the `enabled` uniform (the view's `info.w`), and the size-change rebuild (the size is
in the view). The entry keeps `coreMap` / `lastDraw` for harnesses (`k3-frame-shadows` reads the drawn state from
`entry.coreMap.drawn`).

Not done: the emission light (`emission-light.ts`) is still a TSL port of `vdbEmissionIrradiance`; the same pattern
applies (the core's `outputs.emissionProbes.grid` buffer would need `STORAGE` usage). It also swaps its probe-stack
node's `value` without a rebuild, the class of bug below: follow-up.

## 3. Finding 8: reproduced and fixed

**Reproduced** on `3f81bad` with the new `k3-frame-shadows ?case=shadow&light=spot&mutate=toggle` (the light hidden for
four renders, so the core frees its map and retires the texture and view, then shown again): 5 uncaptured
`Destroyed texture [Texture "vdb three frame volume shadow spot 16"] used in a submit`, and the frame after the light
came back differed from the first (max 255/255). Mechanism: the receivers were built with `entry.map`, a texture node
over the old stand-in; the new map made a new node but no rebuild (same size), so they kept the old texture. The
gate review's (b) case (spectral → grey) rebuilt, so it was safe.

A second three r187 behaviour came out of the fix: three re-reads a render object's object-group bindings (texture and
storage nodes) only on a FULL refresh, and a plain material (`ShadowMaterial`, `MeshStandardMaterial`) that did not
move gets a SHARED refresh. So swapping a node's `value` alone does not reach such a receiver (my first version
submitted the destroyed view buffer on `?mutate=resize`).

**Fix:** each light's texture and storage nodes are made once; their values follow the core (placeholders while the
light has no map: a 1² 2d-array, a 6-layer 1² cube and a zero view, so the receiver returns 1 without sampling); any new
core object (first map, new size, spectral switch, a map gone or back) also rebuilds the light's receivers
(`resetLightShadow`), so they bind the new objects from their next draw, while the core keeps the old ones alive two
more updates. Cube stand-ins get `CubeReflectionMapping` (`CubeTextureNode` logged "Mapping not supported" for point
lights).

**Guards:** `k6-shadows` "spot, light hidden and back" and "spot, map resized and back" (no uncaptured error, the frame
after equals the first, no map while hidden); fail-before: the toggle case on `3f81bad` (above).

## 4. `froxelMix: 'over'`: measured; recommendation **delete** (owner)

one bunny white, the other red absorbing (albedo 0.9, 0.3, 0.2) or dark (albedo 0.1), the colour on either bunny ('over'

**Recommendation:** delete `'over'` (`VDBFrameSettings.froxelMix` becomes 'mixture' only, or the setting goes): it removes
the 'over' gather variants (half the 'volume' gather pipelines), the 'over' branch of `vdbFrameGatherFroxel` /
`vdbFrameGatherFroxelSpectral` and their probes/mutations. Not deleted here (public option, owner's call); the change
is small (settings, gather WGSL generator, twins, `k6-core` probes, the report's `mix*` groups, CHANGELOG, V79).
