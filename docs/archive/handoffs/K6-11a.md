## Task B: naming

Every public core name lost its `Gpu`; `@pmndrs/vdb` and `@pmndrs/vdb/three` now export seven equal names that are different
objects (`CORE_THREE_SAME_NAME` in `api-surface.test.ts`). Inside `./three` the core imports are aliased:
`VDBCoreFrameRenderer`, `VDBCoreFrameVolume`, `VDBCoreSparseSource`, `VDBCoreSparseVolume`, `vdbCoreSparseSource`,
`vdbCoreGridStats`, `vdbCoreDecodeToAtlas` (`three/frame/renderer.ts`, `three/compute.ts`). Nothing else in the tree imported both.

| old | new |
|---|---|
| `vdbGridStatsGpu` | `vdbGridStats` (same name in `./three`) |
| `vdbDecodeToAtlasGpu` | `vdbDecodeToAtlas` (same name in `./three`) |
| `VDBBoxPyramidGpu`, `VDBBoxPyramidGpuOptions` | `VDBBoxPyramid`, `VDBBoxPyramidOptions` |
| `vdbSparseSourceGpu`, `VDBSparseSourceGpu`, `VDBSparseSourceGpuOptions` | `vdbSparseSource`, `VDBSparseSource`, `VDBSparseSourceOptions` (`vdbSparseSource`, `VDBSparseSourceOptions` also in `./three`) |
| `VDBSparseVolumeGpu`, `VDBSparseVolumeGpuOptions`, `VDBSparseLodGpu` | `VDBSparseVolume`, `VDBSparseVolumeOptions`, `VDBSparseLod` (`VDBSparseLod` also in `./three`) |
| `VDBFrameRendererGpu`, `VDBFrameRendererGpuOptions`, `VDBFrameVolumeGpu` | `VDBFrameRenderer`, `VDBFrameRendererOptions`, `VDBFrameVolume` (both also in `./three`) |
| `vdbCreateLevelSetPassGpu`, `VDBLevelSetPassGpu(Options)` | `vdbCreateLevelSetPass`, `VDBLevelSetPass(Options)` |
| `vdbCreatePointPassGpu`, `VDBPointPassGpu(Options)` | `vdbCreatePointPass`, `VDBPointPass(Options)` |
| type `VDBFrameRendererGpu` exported by `./three` | removed (it would collide with the `./three` class `VDBFrameRenderer`); `frameRenderer.core` is typed by the core's `VDBFrameRenderer` |
| `VDBFrameLoader` (core and `./three`) | `VDBSequenceFrameLoader` |
| `wvdbPrefixLength`, `nvdbResponseLength`, `vdbMakeFpNLeafCodec` (`./tools`) | `tools/internal.ts` only |
| internal: `vdbCreateReferenceRendererGpu`, `VDBReferenceRendererGpu`, `VDBReferenceSourceGpu`, class `BoxPyramidGpu` | `vdbCreateReferenceRenderer`, `VDBReferenceRenderer`, `VDBReferenceSource`, `BoxPyramid` |

Left alone on purpose: tools internals `VDBFrameEnvironmentGpuResult` / `environment-gpu.ts` (the CPU twin of the GPU
environment kernel; the name separates it from `VDBFrameEnvironmentResult`), harness-local `GpuJob`, `GpuParityResult`,
`renderGpu`, and `*GpuMs` timing fields (they name the quantity).

`api-surface.test.ts`: rule 3 now allows exactly the seven core / three pairs (a new pair needs the list edited); new rule 4:
no exported name has a `Gpu` suffix (`/Gpu([A-Z]|$)/`) and every name containing `Cpu` has its `Cpu`-less name in core or
`./three`. Snapshots regenerated with `-u` on purpose (core.txt 20 lines, three.txt: `VDBFrameLoader`, `VDBFrameRendererGpu`
out and `VDBSequenceFrameLoader` in, tools.txt: the three helpers out).

Cpu audit (the check you asked for): every `Cpu` name has a twin (`vdbGridStatsCpu`+Options+Result, `vdbDecodeToAtlasCpu`+Options,
`vdbReadValueCpu`, `VDBSampleCpuOptions`). The other way round, CPU functions with a GPU counterpart that carry **no** `Cpu`:
`vdbSampleNearest`, `vdbSampleTrilinear`, `vdbSampleTrilinearVec3` (twins of `./three`'s `vdbSample`; their options type is
`VDBSampleCpuOptions`), `vdbReadValueF32` and `vdbReadValueVec3` (siblings of `vdbReadValueCpu`; same names as the WGSL
readers). Not renamed: the GPU names differ (`vdbSample` vs `vdbSampleTrilinear`), so rule 4 cannot check them, and it
would churn the tools API, the docs and every tools test. Suggestion: leave until the owner decides; if renamed,
`vdbSampleNearestCpu`, `vdbSampleTrilinearCpu`, `vdbSampleTrilinearVec3Cpu`, `vdbReadValueF32Cpu`, `vdbReadValueVec3Cpu`
(pro: one rule; con: five more public renames, WGSL names stay unsuffixed). One test settles it: none; it is a taste call.
