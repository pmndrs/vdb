# K4.22 handoff: partial `.wvdb` LODs while streaming

Branch `worktree-agent-ab103eab7b43de84e`, from `main` at `24895d1`. Owner: T3 (Opus). Date: 2026-11-28.

## Design

The task: while a `.wvdb` LOD streams in, page by page, show it with the coarser LOD upsampled into the bricks that
have not arrived. mjurczyk's worker kernel does this (`wvdbKernel.js` L122–211, L230–344): at a multi-page LOD's first
page it upsamples the previous LOD to the new size, clears the unstored bricks to background, then each page
overwrites its bricks.

**Where the upsample runs.** On the GPU, in the core's dense source, with a CPU twin in `tools`:

- **tools** (`src/tools/wvdb/partial.ts`). `wvdbDensePartialVolume(reader.file, event, { fill, fillMips, …dense })`
  turns any `WvdbStreamReader({ partialLods: true })` event into a `WvdbDenseVolume`. For a partial event, each
  texture's `data` holds the decoded bricks and the background elsewhere, and its `fill` holds:
  - `pending`: one bit per brick, stored and not decoded yet (`mask & ~decoded`; the reader's levels gained a
    `decoded` bitset);
  - `from`: the finest complete coarser LOD's texels (cached per level object, so every page of a LOD shares one
    array);
  - `mips`: `'coarse'` or `'box'`.

  `wvdbDenseResolve(volume)` is the CPU twin: it fills the pending bricks and builds the atlas.
- **core** (`src/core/source/dense-fill.ts`). On `replace` (or construction), the dense source sees a texture with a
  `fill` and runs `VDBDenseFiller`. It uses one storage buffer per channel: pending bits, coarse texels, partial
  texels, then the texture rows and the atlas rows, padded to 256 B. It records one compute pass:
  - `vdbDenseFillCs`, one thread per texel: a pending texel is the upsample, any other texel is the host's;
  - one `vdbDenseMipCs` dispatch per mip level.

  It then calls `copyBufferToTexture` into the source's own textures and submits its own command buffer, as
  `writeTexture` acts on the queue. `r8unorm` is not a storage format in core WebGPU, hence the buffer. The source
  writes bytes with `atomicOr` into cleared words, and an atlas level may start mid-word. With `fill: 'cpu'`, or when
  the buffer would pass `maxStorageBufferBindingSize` or `maxBufferSize`, the source uses the twin, then uploads.
- **What the source sees while bricks are missing.** A normal dense volume of the partial LOD's size. A new size
  bumps `version` (new textures, as for any LOD change). Every page is a same-size `replace` that bumps the new
  `revision`. The stats are the header's baked mean when there is one (scale 1), else those of the decoded texels.
  `maxDensity` also bounds the coarse texels, because an upsampled texel never exceeds them.
- **Integer weights (V163).** His upsample uses an f64 position, f32 weights and nested lerps. Ours uses weights in
  1/256 (the exact fraction rounded half up) and one `(Σ + 2²³) >> 24`, so the GPU and the twin agree byte for byte.
  On halving sizes the result equals his byte for byte; on odd sizes it is off by at most one code.
- **Mip-consistent fill (V164).** This came out of the first A/B, below. Level 1 of a pending brick's atlas is the
  coarser LOD's texel (`fillMips: 'coarse'`, the default). It is not the box filter of the upsample (his
  `frameMipmaps`, kept as `fillMips: 'box'`).

The options give four behaviours, all A/B'd in demo 16: `upsample` (coarse mips), `upsample-box` (his mips),
`background` (`fill: 'background'`, empty bricks), and `off` (the host shows only complete events).

## Found on the way: same-size dense replace never redrew the lighting

The first demo run gave different final frames per mode, though the final LOD's texels were the same. The core frame
renderer's shadow-grid signature and emission-probe key read `slot.version`. A same-size dense `replace` writes into
the same textures and keeps `version`, so the shadow grid kept the content of the pages before. This hits any
same-size dense replace, including `VDBSequence` frames (demo 12), unless the density scale changes.

Fix: `VDBVolumeSourceInfo.revision` (optional). The dense source bumps it on every `replace`, and the two keys
include it. After the fix every mode's final frame equals the direct render (FNV hash). Demo 12, demo 10 and demo 05
e2e pass. Sparse slots are unchanged: their `version` is already the image revision.

- 0 shader or pipeline builds on LOD 2's pages;

## For the owner

**Defaults.** Proposed: `fill: 'upsample'` with `fillMips: 'coarse'`. That is what is shipped and documented.

- Pros: the best mean quality, 6.5 dB over whole LODs only and over his mips, and the picture only gains detail.
- Cons: a LOD's first page is ~1 dB below its coarser LOD; it diverges from his mips (V164).
- What would settle it: the same A/B on a second asset (`bunny_cloud.wvdb`, his bake) and on hardware at quality
  high, with demo 16 `?format=wvdb` and the K4.22 e2e on another file.
