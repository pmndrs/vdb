## What native showed

1. **Our root table order was wrong (fixed).** K4.12 sorted the root table by the unsigned u64 key while the upper
   nodes stayed in signed origin order. Native NanoVDB (a532de55 and v14) keeps OpenVDB's signed `Coord` order for
   both (its root lookup is linear). With the table out of step, `nanovdb_validate` rejected every grid with upper
   nodes on both sides of 0 ("Upper node is not stored breadth-first"; bunny, any negative origin) and
   `parity:native` failed three of the four samples (never rerun since July: it needed Docker). Fix in
   `tools/nanovdb/tree.ts`: the root table now uses the signed origin too. Only root tile entries move (sphere_fog
   Fp8: 88 bytes in the root table); our Fp8 of the native float primitives now differs from native Fp8 in 102
   bytes (checksum and stats) instead of 190. Tests updated on purpose: K4.12 order tests (`inactive-values`,
   `active-tiles`) and the PRE_K46 digests of the straddling grids (`collapse.test.ts`). K7.H1 (c) was this, not
   a v14 change.
2. **`nameKey` was 0 (fixed).** `io::hasGrid(file, name)` needs `nameKey == io::stringHash(name)`, so it reported
   none of our grids (`readGrid` by name accepts 0). `writeNvdb` now writes the hash (`nvdbStringHash`); the native
   value is in the sidecar and the test compares.
3. **Grid-0 readers show the coarsest preview** (`io::readGrid(file)`: `density.lod8`; smoke: `density.lod48`).
4. **Native defect: `io::readGrid(file, n ≥ 1)` in a multi-grid segment** reads grid 0's bytes into a buffer sized
   for grid n (`IO.h` `readGrid(is, n)` applies the accumulated `seek` only after the segment loop): NONE returns
   grid 0 again, ZIP throws "UNZIP failed on byte size", BLOSC "Internal read error in BLOSC". Native files too
   (`two_grids_blosc.nvdb`). K7.12 proposes one segment per grid; K7.13 reports it upstream.
5. **Native defect: `nanovdb_validate` fails every multi-leaf FpN grid** (it steps variable-size leaves by
   `sizeof(LeafNode)`), native `nanovdb_convert --fpN` output included. Our previews are FpN, so `density.lod16`
   "fails"; the Float grid and the single-leaf preview pass.
6. `nanovdb_convert` v14 cannot convert a `HalfGrid` ("Unrecognized OpenVDB grid type"); the HalfGrid oracle stays
   the generator's accessor probes (`vdb-probes.json`).
7. FpN decode: native in f32, fused or not by its build flags; `vdbReadValueCpu` keeps f64. Compare via `fround`
   or `vdbReadValueF32Cpu` (CLAUDE.md trap).
8. Stats: V174 records the Float / Vec3f ave/stddev difference (V73's cause).
