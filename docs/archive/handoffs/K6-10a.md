## The retire-queue choice

**Destroy due objects in a later task (`setTimeout(0)`), on top of the two-update rule.** `VDBRetireQueue.advance()`
no longer destroys; it schedules the due objects for the next task. `retireAfterTask(object)` schedules one without an
update count (for owners with no update: the dense source). `drain()` destroys everything at once.

Why this and not the alternatives:

- WebGPU lets you `destroy()` an object a *submitted* command buffer uses (the free waits for the GPU); only a submit
  that names an already destroyed object fails. So the only thing a retire has to wait for is the host's submit,
  not `onSubmittedWorkDone()`.
- The core never sees that submit. `queue.onSubmittedWorkDone()` taken in `update()` can resolve before the host
  submits the encoder that update recorded (it covers what was submitted so far), so it is not submit-safe by itself.
- A host records and submits a frame in one task (one `requestAnimationFrame` callback), even when it records several
  updates or pass records into one encoder. A destroy in a later task is after that submit. The two-update rule stays,
  so a host that keeps the documented contract (one update per submit) is safe even across tasks.
- The remaining unsafe pattern is three or more updates recorded without a submit AND an `await` between record and
  submit. The docs (`renderer.ts` header, `rendering-without-three.mdx` step 7, `dense.ts` `replace`) say to submit in
  the task that recorded.
- Enforcing the limit with an error was the other option: the core cannot see submits, so the only detectable case is
  the same `GPUCommandEncoder` passed to two `update()`s, which misses separate encoders submitted together and would
  throw on a pattern that is safe within a task. It catches less and breaks more.
- Cost: one timer per update that has due objects (rare: a resize, a growth); no extra GPU work. Retired memory lives
  one task longer.

The sparse source (`vdbSparseSourceGpu`, own retire list) and the dense source use the same queue class; the level-set
and point passes already did. The pool's own growth retire (`settled()`) and the reference renderer's `setScene` are
unchanged (follow-ups).

## Proposal for the owner: public names (no rename made)

Question: rename before 0.2.0 ships (no aliases, Q6), or freeze as is?

1. **The `Gpu` suffix.** `vdbCreateLevelSetPassGpu` / `vdbCreatePointPassGpu` carry it in the function name; their
   siblings `vdbCreateFrameRenderer` (→ `VDBFrameRendererGpu`) and `vdbCreateBoxPyramid` (→ `VDBBoxPyramidGpu`) don't.
   - Suggestion: drop it from the two function names (`vdbCreateLevelSetPass`, `vdbCreatePointPass`) and keep it on
     the returned types, the rule the frame renderer and pyramid already follow. In the core every `vdbCreate*` makes
     GPU objects, so the suffix carries no information in a function name; the type suffix distinguishes core objects
     from `./three` classes (`VDBFrameRenderer` vs `VDBFrameRendererGpu`).
   - Pros: one rule, shorter names, matches the two older APIs (0.1.0's `vdbCreateBoxPyramid`).
   - Cons: two more renames in a release that already renames `./three`; demo 17 and the docs change.
   - Settles it: `test/api-surface.test.ts` naming rule extended with "a `vdbCreate*` function has no `Gpu` suffix"
     (fails today on the two).
2. **Internal-looking public names** (`VDB_GPU_LAYOUT_VERSION`, `WvdbLayout`, `wvdbPrefixLength`, also
   `VDBFroxelLayout`, `VDBBoxPyramidLayout`, `nvdbResponseLength`, `vdbMakeFpNLeafCodec`).
   - Suggestion: keep `VDB_GPU_LAYOUT_VERSION` public (a host that caches pool bytes needs it to invalidate) and the
     `*Layout` result types that public functions return; move `wvdbPrefixLength`, `nvdbResponseLength` and
     `vdbMakeFpNLeafCodec` to `tools/internal.ts` (their callers are our streaming readers, the quantizer, `./three`'s
     coarse-first loader and tests).
   - Pros: a smaller frozen surface before more consumers (cloud system, pathtracer) depend on it.
   - Cons: a breaking removal for anyone who imported them: all three are public since 0.1.0 (`4cc83ab`).
   - Settles it: `grep` the consumer repos (read-only) for the names; if none uses them, move them.
3. `VDBSparseIndexBox` (core) vs `VDBIndexBox` (three), and `VDBFrameLoader` (sequences) in the froxel `VDBFrame*`
   namespace: suggest `VDBSequenceFrameLoader` for the latter (the sequence's option type); the boxes describe different
   things (index vs world-to-index) and can stay.
